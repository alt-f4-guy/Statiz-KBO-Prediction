# KBO 운영 검증 강화 설계

## 목표

2026-07-28부터 실시간 예측과 Statiz 제출을 재개하기 전에 다음 조건을 만족한다.

- 경기 시작 이후 신규 예측과 전송이 생성되지 않는다.
- 전향적 평가 표본이 공학적 회귀 검사 표본과 섞이지 않는다.
- API 전송 성공률, 대체 모델 사용률, 라인업 완성률과 피처 사전분포 사용률을 예측 당시 로그로 계산할 수 있다.
- 통계 판정의 기준선, 차이 방향, 재표본 방식과 판정 우선순위가 고정된다.
- 실행 경로, 테스트 명령, 모델 메타데이터와 검증 계획이 현재 저장소 구조와 일치한다.

## 범위

### 포함

- `scripts/ops/predict_2026.py`의 경기 시작 시각 게이트와 추가 전용 운영 로그 보강
- `scripts/ops/evaluate_prediction_log.py`의 전향적 표본 선택, 운영 지표, 확률 지표와 통계 판정
- 관련 단위 테스트
- 배포 메타데이터의 프로젝트 상대 경로와 재현성 정보
- 현재 저장소 구조에 맞춘 `docs/remaining_verification_plan.md`
- 인증 정보를 저장하지 않는 실제 읽기 API 스모크 검증

### 제외

- 대상 경기가 없는 상태에서 임의의 `s_no`로 `prediction/savePrediction`을 호출하는 행위
- 모델 재학습, 하이퍼파라미터 변경, 피처 정의 변경
- 별도 데이터베이스나 신규 운영 프레임워크 도입

## 설계

### 1. 실시간 예측 시간 게이트

신규 예측을 만들기 전에 현재 UTC 시각과 `game_datetime`을 비교한다. 현재 시각이 경기 시작 시각 이상이면 예측과 전송을 모두 건너뛰고 `expired` 운영 이벤트만 남긴다. 기존에 경기 전에 고정된 예측이 있더라도 경기 시작 이후에는 재전송하지 않는다.

시간 판정은 부작용이 없는 작은 함수로 분리하여 경계값을 단위 테스트한다.

### 2. 추가 전용 운영 로그

기존 CSV 추가 기록 방식을 유지한다. 최초 `prediction` 행에는 다음 감사 필드를 추가한다.

- `deployment_id`
- `evaluation_role`
- `prospective_start_date`
- `lineup_complete`
- `feature_prior_usage_rate`
- `model_checksum`
- `data_checksum`
- `split_manifest_checksum`

`delivery` 행에는 최종 `success` 또는 `failed` 상태와 비밀값을 제외한 오류 유형을 기록한다. 재시도별 상세 행은 만들지 않고, 경기별 최종 전송 결과만 저장한다. 기존 로그 행은 수정하지 않는다.

### 3. 전향적 평가 코호트

평가 대상은 다음 조건을 모두 만족해야 한다.

1. `record_type == "prediction"`
2. `recorded_at < game_datetime`
3. 최초 예측
4. `evaluation_role == "prospective_holdout"`
5. `recorded_at`이 `prospective_start_date` 이상
6. 지정된 `deployment_id`와 일치
7. 비무승부 종료 경기

성과 지표는 모든 유효 예측과 성공적으로 제출된 예측을 구분한다. 모델 유형별 성능은 분리하되, 대체 모델 사용률과 API 저장 성공률은 기간 전체를 분모로 계산한다.

### 4. 지표와 통계 판정

고정 기준선은 배포 시점 학습 구간인 2023~2025년 비무승부 경기의 홈 승률로 계산하고 배포 메타데이터에 저장한다. 전향적 경기 결과로 기준선을 갱신하지 않는다.

경기별 손실 차이는 다음과 같이 정의한다.

```text
로그 손실 차이 = 모델 로그 손실 - 기준선 로그 손실
브라이어 차이 = 모델 브라이어 점수 - 기준선 브라이어 점수
```

음수는 모델 우위, 양수는 기준선 우위다. 경기일을 재표본 단위로 하는 짝지은 블록 부트스트랩 2,000회와 시드 42를 사용한다.

판정 우선순위는 다음과 같다.

1. 데이터 파이프라인 점검
2. 모델 재검토
3. 재보정 검토
4. 추가 관찰
5. 유지

100경기에서는 경고만 산출한다. 300경기 이상에서 첫 운영 판정을 산출하며, 단일 클래스 또는 10경기 미만 세그먼트의 계산 불가 지표는 `NaN`으로 기록한다.

### 5. 재현성

배포 식별자는 Git 커밋과 모델·데이터·시간 분할 명세의 SHA-256 체크섬으로 구성한다. 모델 메타데이터의 파일 경로는 프로젝트 상대 경로로 저장한다. 로그에는 비밀값, 서명 헤더와 전체 API 응답을 기록하지 않는다.

### 6. API 검증

유효한 인증 정보로 다섯 읽기 엔드포인트를 실제 호출한다. 검증 결과에는 호출 시각, 엔드포인트, HTTP/응용 결과 상태, 필수 필드 존재 여부와 행 수만 기록한다.

오늘은 제출 가능한 경기가 없으므로 쓰기 API는 모의 응답으로 다음을 검증한다.

- `percent == P(Home) × 100`
- 원정 우세에서도 확률을 뒤집지 않음
- 동일 확률 재시도
- 성공 전 처리 완료 금지
- 최종 실패 로그 기록

실제 쓰기 계약 검증은 대상 경기가 존재할 때 별도 승인된 `s_no`로 수행한다.

## 오류 처리

- 인증 누락은 네트워크 호출 전에 실패한다.
- 경기 시작 이후 대상은 예측·전송하지 않는다.
- 읽기 API 계약 불일치는 후속 수집을 중단한다.
- 쓰기 API 최종 실패는 예측을 보존하고 실패 전달 행을 추가한다.
- 평가 코호트 필수 감사 필드가 없으면 전향적 판정을 중단하고 명시적 오류를 낸다.

## 테스트 전략

각 동작은 실패 테스트를 먼저 실행한 뒤 최소 구현으로 통과시킨다.

- 경기 시작 직전 허용, 시작 시각과 이후 차단
- 전향적 역할·시작일·배포 식별자 필터
- 실패 전달 행과 API 성공률
- 기간 전체 대체 모델 사용률
- 사전분포 사용률과 라인업 완성률
- 단일 클래스·소표본의 `NaN`
- 고정 기준선과 손실 차이 방향
- 날짜 블록 부트스트랩의 시드 42 재현성
- 판정 우선순위
- 프로젝트 상대 메타데이터 경로
- 전체 53개 기존 회귀 테스트

## 완료 기준

- 신규·기존 단위 테스트가 모두 통과한다.
- 계획에 기록된 표준 테스트 명령이 실제로 성공한다.
- 실제 읽기 API 스모크 검증이 비밀값 노출 없이 통과한다.
- 외부 쓰기 API 호출 없이 쓰기 계약의 로컬 검증이 통과한다.
- 전향적 평가 시작 전에 필요한 모든 감사 필드가 코드와 문서에 반영된다.
