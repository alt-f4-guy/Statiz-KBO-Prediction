# 데이터 분석가 포트폴리오 README 설계

## 1. 목적

현재 README를 실행 안내 중심 문서에서 데이터 분석가 채용 포트폴리오로
개편한다. 문서는 채용 담당자와 현업 데이터 분석가가 상단에서 프로젝트의
문제·규모·성과를 빠르게 파악하고, 데이터 사이언티스트와 기술 면접관이
하단에서 데이터 누수 방지, 피처 설계, 모델 선택, 검증, 운영 근거를 확인할
수 있는 포트폴리오 퍼널 구조를 사용한다.

README는 프로젝트의 실제 코드와 저장된 산출물로 확인되는 사실만 사용한다.
팀 성과와 개인 기여를 구분하며, 모델 성능을 과장하지 않는다.

## 2. 독자와 핵심 메시지

### 2.1. 주요 독자

- 채용 담당자와 현업 데이터 분석가
- 데이터 사이언티스트와 기술 면접관

### 2.2. 핵심 메시지

이 프로젝트는 2인 팀이 KBO 경기 전 홈팀 승리 확률을 예측하기 위해 데이터
수집, 시점 기준 피처 생성, 확률 모델 비교, 순차 검증, 실시간 API 제출과
운영 로그 평가를 하나의 파이프라인으로 구축한 사례다.

정확도 한 개를 높이는 것보다 다음 분석 원칙을 우선했다.

- 경기 시작 전 이용 가능한 정보만 사용하는 시점 일관성
- 시간 순서를 지킨 개발·보정·최종 평가 분리
- 로그 손실, 브라이어 점수, 보정 품질 중심의 확률 모델 선택
- 결측·소표본·API 실패 상황을 기록하고 대체 모델로 처리하는 운영 안정성

있어야 한다. 하단 섹션은 주장에 대한 기술 근거와 재현 경로를 제공한다.

## 4. 섹션별 내용

### 4.1. 프로젝트 제목과 한 문장 요약

제목은 KBO 홈팀 승리 확률 예측이라는 분석 대상을 명확히 드러낸다. 부제는
Statiz API 기반 데이터 수집부터 실시간 예측 제출까지 구현한 엔드투엔드
확률 예측 파이프라인임을 설명한다.

### 4.2. 프로젝트 한눈에 보기

다음 사실을 간결한 표로 제시한다.

- 프로젝트 형태: 2인 팀 프로젝트
- 분석 기간: 2023~2026년
- 최종 피처 데이터: 2,608경기, 66개 열
- 예측 목표: 무승부를 제외한 조건부 홈팀 승리 확률
- 운영 모델: CatBoost 직접 분류기
- 검증 구조: 2025년 순차 개발 폴드 3개, 2026년 최종 평가
- 구현 범위: 수집, 정형화, 피처, 모델 비교, 실시간 추론, API 제출, 운영 로그

### 4.3. 문제 정의와 분석 목표

단순 승패 적중 문제가 아니라 경기 시작 전에 이용 가능한 데이터만으로
확률의 품질과 보정 상태를 관리하는 문제로 정의한다. API에 전송하는
`percent`는 항상 홈팀 승리 확률이라는 운영 계약도 명시한다.

### 4.4. 핵심 분석 과제와 해결 방식

“문제 → 조치” 표로 다음 내용을 설명한다.

- 경기 후 데이터가 같은 경기 피처에 섞이는 시점 누수
- 시즌 초와 신규 선수의 소표본 변동성
- 선발·타선·불펜의 서로 다른 데이터 단위
- 정확도 중심 모델 선택의 한계
- 불완전한 라인업과 API 실패 상황

각 항목은 경기 직전 컷오프, 과거 기록 축소 추정, 로스터 기반 역할 구분,
확률 평가 지표, 최근 10경기 대체 모델과 추가 전용 로그로 연결한다.

### 4.5. 데이터 구성과 피처 설계

데이터 흐름은 일정, 라인업, 로스터, 선수 일별·시즌 기록에서 경기 단위
피처로 이어지는 구조로 설명한다. 주요 피처 그룹은 다음과 같다.

- 선발 투수: FIP와 데이터 출처·결측 상태
- 타선: OBP, SLG, ISO, BB%, K%, 선형 득점 기여
- 불펜: FIP, ERA, K/BB, 최근 1일·3일·10경기 투구 부담
- 환경: 연도별 리그 상수와 구장 팩터
- 상대 비교: 홈·원정 피처 차이

모든 피처에는 경기 시작 직전 컷오프를 적용하고, 리그 사전분포 또는 과거
기록 축소 추정의 출처를 감사 열로 남긴다는 점을 강조한다.

### 4.6. 검증 전략

시간축을 지키는 검증 구조를 Mermaid 다이어그램으로 표현한다.

- 초기 학습: 2024년까지의 과거 경기
- 개발 검증: 2025년 시간 순서 확장형 폴드 3개
- 보정 구간: 2025년 후반 별도 구간
- 최종 평가: 2026년 438개 비무승부 경기

2026년 성능은 개발 폴드에서 운영 모델을 선택한 이후의 공학적 최종 평가이며,
2026-07-28 이후 고정 배포에서 생성되는 전향적 운영 예측과 구분한다.

### 4.7. 모델 비교와 선택 결과

다음 모델을 하나의 표로 비교한다.

| 모델 | 개발 로그 손실 | 개발 브라이어 | 2026 로그 손실 | 2026 브라이어 | 2026 ROC AUC | 정확도 |
|---|---:|---:|---:|---:|---:|---:|
| CatBoost | 0.675058 | 0.241126 | 0.684634 | 0.245763 | 0.584988 | 0.568493 |
| 로지스틱 회귀 | 0.718816 | 0.259393 | 0.684957 | 0.245913 | 0.583090 | 0.573059 |
| 음이항 득점 모델 | 0.786685 | 0.274557 | 0.688316 | 0.247589 | 0.598611 | 0.536530 |
| 포아송 CatBoost 득점 모델 | 0.694530 | 0.249909 | 0.692261 | 0.249443 | 0.547584 | 0.547945 |
| 고정 홈 승률 기준선 | 해당 없음 | 해당 없음 | 0.692985 | 0.249919 | 0.500000 | 0.511416 |

CatBoost가 정확도 최고 모델이 아니라는 점을 숨기지 않는다. 개발 폴드의
로그 손실과 브라이어 점수가 가장 낮고 확률 보정 품질을 함께 고려했기 때문에
운영 모델로 선택했다는 의사결정을 설명한다.

### 4.8. 운영 파이프라인

다음 흐름을 Mermaid 다이어그램으로 표시한다.

```text
Statiz API
→ 일정·라인업·로스터·선수 기록 수집
→ 원천 스냅샷 정형화
→ 시점 기준 v9 피처 생성
→ CatBoost 또는 최근 10경기 대체 확률
→ prediction/savePrediction 제출
→ 추가 전용 운영 로그
→ 주간·월간 확률 품질 평가
```

재시작 시 완료 경기 복원, 경기 시작 후 신규 제출 차단, API 저장 재시도,
배포 ID와 체크섬 기록을 운영 안전장치로 요약한다.

### 4.9. 팀 구성과 담당 역할

“2인 팀 프로젝트”를 명시한다. 개인 기여는 팀 전체 구현과 분리해 사용자가
직접 채울 수 있도록 다음 항목의 작성 틀을 제공한다.

- 담당 영역
- 주요 구현 및 분석
- 핵심 의사결정
- 협업 방식
- 기여 결과

개인 기여가 작성되기 전에는 팀 전체 성과를 특정 개인의 단독 성과로 표현하지
않는다.

### 4.10. 재현 방법

다음 내용만 유지한다.

- Python 3.14와 주요 의존성 설치
- `config/.env.example` 기반 인증 설정
- 실제 데이터 비공개 환경을 위한 고정 시드 42 합성 예시 데이터
- 일일 운영 파이프라인 실행
- 모델 튜닝, 백테스트, 운영 로그 평가의 개별 명령

현재 `run_pipeline.py`는 일일 수집·정형화·실시간 예측 흐름이며 모델 튜닝과
학습 전체를 자동 실행하지 않는다는 실제 동작을 정확히 설명한다.

### 4.11. 저장소 구조와 상세 문서

전체 파일 목록 대신 분석 흐름을 이해하는 데 필요한 디렉터리만 보여준다.
세부 운영 설계는 `docs/pipeline_summary.md`, 합성 데이터는
`examples/README.md`, 평가 산출물은 `artifacts/evaluations/`로 연결한다.

### 4.12. 한계와 다음 단계

다음 한계를 명시한다.

- 시즌 초와 신규 선수는 리그 사전분포 의존도가 높다.
- 2026 최종 평가는 운영 전향적 홀드아웃과 동일하지 않다.
- API 호출 제한과 라인업 공개 시점에 따라 대체 모델이 사용될 수 있다.
- 실제 데이터 공개와 재현은 Statiz API 정책과 데이터 사용 권한에 제약받는다.

다음 단계는 전향적 표본 축적, 확률 보정 안정성 점검, 대체 모델 사용률과 API
성공률 모니터링으로 제한한다.

## 5. 문체와 형식

- 한국어로 작성한다.
- 제목과 표를 사용하되 과도한 배지와 장식용 이미지는 사용하지 않는다.
- 상단은 비기술 독자도 이해할 수 있는 평문을 사용한다.
- 하단은 데이터 누수, 시점 결합, 평가 지표와 운영 계약을 정확히 표현한다.
- 성능 비교와 통계 수치는 반드시 Markdown 표로 제시한다.
- 수치는 저장된 CSV와 JSON 산출물의 정밀도를 유지하거나 소수 넷째 자리로
  일관되게 반올림한다.
- README 전체는 약 250~350줄을 목표로 한다.

## 6. 변경 범위

수정 파일은 `README.md` 하나로 제한한다. 설계와 구현 계획 문서는
`docs/superpowers/` 아래에 별도로 남긴다. 기존 코드, 데이터, 모델 산출물,
테스트, 사용자 미커밋 변경은 수정하지 않는다.

## 7. 검증 기준

README 개편 완료 전 다음을 검증한다.

1. 모든 성능 수치가 `artifacts/evaluations/model_comparison_results.csv`와
   일치한다.
2. 데이터 규모가 `data/final/final_training_set_v9.csv`와 일치한다.
3. 시간 분할 설명이 `data/final/time_split_manifest.json`과 일치한다.
4. 운영 모델과 선택 규칙이 `artifacts/models/best_model_metadata.json`과
   일치한다.
5. 실행 명령이 현재 파일 구조와 모듈 경로를 사용한다.
6. README 내부 상대 링크가 모두 존재한다.
7. 비밀값, 개인 식별자, 공개할 수 없는 원천 데이터가 포함되지 않는다.
8. 팀 성과와 개인 기여가 구분되어 있다.
9. `git diff --check`를 통과한다.
